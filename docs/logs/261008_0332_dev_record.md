## 3. 調查時確認的事實

### 3.1 「RTP 接收端」其實只需要 WebRTC

- **前端：**`imood_ai.html` 只會做一件事，就是 `POST {media}/offer`。
  - 拿到的 video、audio 直接接到頁面上的 `<video>`、`<audio>`，**沒有跳出播放視窗**。
  - debug 數字（fps、掉幀、jitter）是前端自己用 `getStats()` 算的。
- **模型：**:8010 的 LiveTalking + Wav2Lip 就是取代 JoyGen 的模型，**只輸出 WebRTC**（`/offer`、`/whep`）。
- **結論：**RTP 原本只是預想的替代方案，這次**整個放棄**，照 LiveTalking 的方式接 WebRTC。

### 3.2 sessionid 由 LiveTalking 產生，而且綁定那一條連線

`session_manager.create_session(params)` 用 uuid 產生 sessionid，`avatar` 也從 `params` 讀。
語音服務在 `/api/ask` 會先查 `/api/admin/sessions`，確認這個 session 還活著，再往 `/cyber_gf/audio_stream?sessionid=` 推聲音。
所以 B 只要把 LiveTalking 回傳的 sessionid **原封不動**交給前端，id 就一定對。

### 3.3 斷線清理 LiveTalking 已經自己做了

`server/rtc_manager.py` 在 peer connection 變成 `failed`／`closed` 時，會呼叫 `session_manager.remove_session(sessionid)`。
做法 1 的 WebRTC 是瀏覽器直接連 LiveTalking，所以前端 `pc.close()` 之後，LiveTalking 會自己刪 session，**B 不用寫任何清理程式**。實測確認。

## 4. 決策過程

| 決策 | 選擇 | 原因 |
|---|---|---|
| 接收端做法 | **做法 1：只轉發協商** | 不確定組裡有沒有「影像要經過 B」的需求。之後可能上雲端 A100，做法 2 要解碼再重新編碼，多 20–60 ms 延遲，也多吃 CPU/GPU。先不要過度設計 |
| 保留升級空間 | 向 LiveTalking 協商的程式集中在 `negotiate_with_livetalking()` | 升級成做法 2 時只換這個函式，`/offer` 對前端的介面不變 |
| 何時升級做法 2 | 有其中一個需求時 | (1) 要在 B 加浮水印、錄影或轉送；(2) 雲端只開 TCP，必須由 B 處理 TURN，B 跟 LiveTalking 之間走 localhost |
| RTP | 放棄 | 上游沒有 RTP 輸出，前端也只認 WebRTC |
| 程式放哪 | Windows 這份是唯一原始碼，單向同步到 `/root/imood_rtp`（之後改成 git：Windows push、WSL `git pull`） | 兩邊都要有一份，但只能有一個地方可以改，避免版本分岔 |
| `/offer` 內容 | 整包轉給 LiveTalking | 除了 `avatar`，其他欄位也會傳到 `create_session(params)`，跟直接連 LiveTalking 的行為完全一樣 |

## 6. 遇到的問題

| 問題 | 處理 |
|---|---|
| 從 Git Bash 呼叫 `wsl ... cat /root/...` 時，路徑被改寫成 `C:/Program Files/Git/root/...` | 加上 `MSYS_NO_PATHCONV=1` |
| 用 `wsl -- bash -c '...'` 帶迴圈時，`$d` 這類變數會消失 | 改成先寫成腳本檔，再用 `bash <檔案>` 執行 |
| Python 3.10 的 `asyncio.TimeoutError` 不等於內建的 `TimeoutError`（3.11 才合併） | `except asyncio.TimeoutError`，否則 LiveTalking 逾時會變成 500 錯誤，而不是 `{code:-1, msg}` |
| Chrome 擴充功能沒有連上 | 改用 aiortc 無頭客戶端，模擬 `imood_ai.html` 的 offer（先 video 後 audio、recvonly、帶 avatar）；真實瀏覽器測試改由使用者執行 |
| 第 3 項卡在 LLM | :8090 沒有啟動（Windows 端，A 負責）。測試紀錄標為**未完成** |

### 已知問題

| 問題 | 說明 |
|---|---|
| `/offer` 約 5.3 秒 | 時間花在 LiveTalking 建 session，B 本身幾乎不花時間。前端在這段時間會顯示「連線中…」 |

| 開發機預設的 WSL distro 是 22.04 | 所有指令都要明確寫 `wsl -d Ubuntu-24.04` |

### 之後上雲端 A100（這次不做）

- 做法 1 是瀏覽器**直接連** LiveTalking 的隨機 UDP port。預計用「防火牆開放 UDP」或 localhost 的方式解決。
- 平台如果只開 TCP，需要 TURN，或升級成做法 2。
- 不是 localhost 的話，瀏覽器麥克風需要 **HTTPS**。

## 11. 給組長的三點

1. **B 目前只轉發協商，影像不經過 B。** 這樣做零延遲，sessionid 也一定對。
   協商的程式獨立成一個函式，之後需要碰影像（浮水印、錄影、雲端 TURN），只要換掉這個函式，前端不用改。
2. **第 3 項（對嘴）還沒驗證。** 語音服務接受了 sessionid，LiveTalking 也在同一個 session 登記了這次發話，
   但 LLM 沒有啟動，聲音一直沒產生。要等 llama-server 啟動後重測。
3. **上雲端 A100 要先確認平台能不能開放 UDP。** 如果只能開 TCP，就要 TURN 或升級成做法 2。
